# Uni Kasher Desktop 2.0

> نظام إدارة أعمال سريع للتجار والبياعين — مبيعات، مخزون، خزنة، موردين، عملاء، مصروفات وحسابات عامة، مع SQLite محلية وتشغيل أساسي بدون إنترنت.

## ماذا يدير Uni Kasher؟

- **نقطة البيع:** باركود، سلة، خصومات، طرق دفع، تعليق فواتير وطباعة.
- **المخزون:** منتجات، فئات وSubcategories، حركات المخزون، التسويات، حد الطلب والركود.
- **الموردون:** مشتريات، دفعات متعددة، كشف حساب، إجمالي المشتريات والمدفوع والمتبقي.
- **الخزنة:** افتتاح/إغلاق، دخول/خروج، مصروفات، فرق الخزنة، ومنع الرصيد السالب.
- **الحسابات العامة:** Dashboard مالي حي مبني على حركات التشغيل الفعلية، لا على بيانات منفصلة.
- **العملاء والولاء:** بيانات العملاء والنقاط والمعاملات.
- **التقارير والتنبيهات:** ربحية، حركة بيع وشراء، مخزون راكد، نقص مخزون ومؤشرات تشغيل.
- **النسخ الاحتياطي:** تصدير واستعادة/دمج مع حماية العلاقات والبيانات المشتقة.

## مبدأ معماري أساسي

```text
UI
 ↓
desktopApiFetch()
 ↓
desktop-api.ts
 ↓
desktop-core/*  ← validation / auth / SQL helpers
 ↓
SQLite
```

SQLite هي **مصدر الحقيقة الوحيد**. أي Dashboard أو تقرير أو حساب مالي يجب أن يقرأ من نفس حركات التشغيل، ولا يعيد تنفيذ منطق آخر منفصل.

## هيكل المشروع

```text
src/
├── desktop/              # تشغيل واجهة Tauri
├── components/           # واجهة الوحدات وPOS
├── lib/
│   ├── desktop-api.ts    # orchestration + domain handlers
│   ├── desktop-core/     # قواعد مشتركة: auth, validation, SQL
│   ├── types/            # عقود البيانات المشتركة
│   └── *.ts              # سياسات/حسابات صغيرة قابلة للاختبار
├── hooks/
└── ...

migrations/sqlite/        # migrations مرتبة للديسكتوب
src-tauri/                # Rust/Tauri shell
```

## التطوير

المتطلبات: Node.js، Rust، أدوات بناء Windows، وWebView2.

```bash
npm install
npm run dev
npm run test
npm run lint
npm run build
npm run tauri:build
```

`npm run build` يبني واجهة Vite إلى `src-tauri/dist`، بينما `npm run tauri:build`
يبني تطبيق Tauri/installer.

## قواعد التطوير

1. أي قاعدة مالية أو مخزنية توضع في طبقة desktop-core/domain أو SQLite، وليس في UI فقط.
2. أي تغيير في الـschema يأتي في migration جديدة.
3. لا تضف API ثانية لنفس العملية.
4. قبل إضافة Feature جديدة، ابحث عن مصدر الحقيقة الحالي واجعل الـDashboard والتقارير تقرأ منه.
5. استخدم comments لشرح **سبب** القرار عندما يكون غير واضح؛ لا تكرر ما يقوله الكود.
6. أي عملية مالية قابلة لإعادة الإرسال تحتاج idempotency.
