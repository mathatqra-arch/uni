# NexFlow Desktop 2.0.2 — Final Hardening & Anti-Koshary Report

## Scope
Desktop-only NexFlow POS. SQLite is the operational source of truth. No cloud/remote transport is part of the runtime.

## Hardening completed

### Architecture
- SQLite is the single operational data source.
- Automatic accounting journal construction was extracted into `src/lib/desktop-core/accounting.ts`.
- Validation, auth, SQL infrastructure, dead-stock policy, and SKU policy remain isolated under `desktop-core`/`lib`.
- Legacy Web/Next/Supabase/Prisma/Dexie runtime paths are rejected by the verification gate.
- Local `sync_queue` is treated as a local operation journal for audit/idempotency compatibility, not a network transport.

### Financial and inventory invariants
- Cash opening cannot be negative.
- Cash movements must use positive amounts and cannot take an open drawer below zero.
- Supplier payment history is immutable and duplicate-safe through transaction identifiers.
- Journal lines cannot contain negative values or both debit and credit at once.
- Stock movement journal is authoritative; derived `current_stock`/`stock_levels` are rebuilt and checked for drift.
- Negative stock is blocked at the SQLite layer unless explicitly allowed per product.
- Automatic journal entries are generated by operational transactions rather than relying on a disconnected manual ledger.

### Backup and restore
- Backup export is encrypted in the UI using AES-256-GCM with PBKDF2-SHA256 key derivation.
- Restore supports preview/dry-run before writes.
- Restore is transaction-safe and merges rather than blindly appending.
- IDs are remapped across related tables.
- Derived `stock_levels`, product `current_stock`, product `avg_cost`, and purchase `paid_amount` are not treated as authoritative imported values; they are rebuilt/reconciled from source records.
- Open local cash sessions are protected from being silently replaced by an incoming open session.

### License
- Ed25519 signatures remain the trust anchor.
- Stored license, last-seen timestamp, activation timestamp, and used-license history are protected with Windows DPAPI when running on Windows.
- Device binding prefers Windows MachineGuid and falls back to a stable installation ID instead of mutable username/computer name values.
- License verification uses one shared signed-payload parser to prevent cryptographic-check drift.

### Product and SKU
- Product category is mandatory.
- Product commercial acquisition price is kept synchronized between the new purchase-cost field and the legacy wholesale-price database field.
- Category/subcategory-aware SKU generation is centralized and sequence-backed.

### Dead stock
- Resolution precedence is product override → subcategory override → category override → global default.
- Global default is 60 days.
- Dashboard totals are calculated from the complete matching set, not from a limited preview list.
- New products are not incorrectly marked dead before their effective threshold.

### Security and UI safety
- Authentication tokens are not persisted to `localStorage`.
- `dangerouslySetInnerHTML`, `document.write`, popup execution paths, and local `/api` fallbacks are blocked by the release verification gate.
- Tauri filesystem permissions were narrowed from the default permission set to the specific text read/write capabilities used by backup/export flows.

## Verification limitations

A complete `npm test`, `npm run lint`, Vite production build, and Tauri Windows installer build were not executable in this environment because the project dependency tree was incomplete and Rust/Cargo are not installed here. The final release archive therefore does not claim a Windows installer/build pass.

## Recommended release gate on Windows

```powershell
npm install
npm run verify
npm run verify:sqlite
npm test
npm run lint
npm run build
npm run tauri:build
```

Then run the end-to-end smoke scenario on a copy of the database:

`purchase → supplier payment #1 → supplier payment #2 → sale → split payment → refund → expense → cash close → dashboard → general accounts → encrypted backup → dry-run restore → merge restore → integrity check`.
